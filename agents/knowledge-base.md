# Knowledge Base - Domain & Product-Specific Information

This file contains domain knowledge about the MeetSynq product and codebase. For coding guidelines and rules, see [`rules/`](rules/).

## When working with managed event types

When a managed event type is created, we create:
- A **parent managed event type** for the team (has `teamId` set in EventType table)
- A **child managed event type** for each assigned user (has `userId` set in EventType table)

Example: If we create a managed event type and assign Alice and Bob, three rows will be inserted in the EventType table (1 parent + 2 children).

**Important**: Only child managed event types can be booked.

## When working with organizations and teams

Both organizations and teams are stored in the `Team` table:
- **Organizations**: Have `isOrganization` set to `true`
- **Teams within an organization**: Have `parentId` set (pointing to the organization)

## When working with OAuth clients

There are two types of OAuth clients:

| Type | Table | Purpose |
|------|-------|---------|
| OAuth client | `OAuthClient` | Allows 3rd party apps to connect users' cal.com accounts |
| Platform OAuth client | `PlatformOAuthClient` | Used by platform customers integrating cal.com scheduling directly in their platforms |

If someone says "platform OAuth client" they mean the one in the `PlatformOAuthClient` table.

## When you need product or codebase context

### Monorepo Structure

The whole repository is a monorepo. The main web app is in `apps/web` folder.

### Local Development Database

When setting up local development database, it creates test users. The passwords are the same as the username:
- `free:free`
- `pro:pro`

### Logging Levels

Control logging verbosity by setting `NEXT_PUBLIC_LOGGER_LEVEL` in .env:
- 0: silly
- 1: trace
- 2: debug
- 3: info
- 4: warn
- 5: error
- 6: fatal

### MeetSynq Event Identification

`packages/features/calendar-subscription/lib/sync/CalendarSyncService.ts` filters synced events by
`iCalUID?.toLowerCase()?.endsWith("@cal.com")`. This is inherited upstream behavior — `iCalUID` is
generated by the external calendar provider (e.g. Google), not manufactured by our own booking code,
so this filter predates and is unrelated to the MeetSynq rebrand. Flagged, not yet fixed upstream.

### UI Component Locations

- Event types page: `apps/web/modules/event-types/views/event-types-listing-view.tsx`
- Bookings page: `apps/web/modules/bookings/views/bookings-view.tsx`
- Shared elements (tabs, search bars, filter buttons) should maintain consistent alignment across views

### DataTable

Refer to the DataTable guide at `packages/features/data-table/GUIDE.md` for implementation patterns and best practices.

### Round-Robin Scheduling

Reuse existing code in `packages/features/bookings/lib/getLuckyUser.ts` which handles:
- Weight-based selection
- Priority ranking
- Round-robin fairness algorithms

Check if existing functions can be extended before creating new implementations.

### Calendar Cache System

The calendar cache system follows specific patterns in `packages/features/calendar-cache-sql`. When implementing provider-specific calendar cache services (like for Outlook/Office365), place the provider-specific code in the corresponding provider directory (e.g., `packages/app-store/office365calendar`).

### API Documentation

The OpenAPI specification at `docs/api-reference/v2/openapi.json` is auto-generated from NestJS controllers. Manual edits will be wiped out.

To make persistent changes to API documentation, use NestJS decorators (`@ApiQuery`, `@ApiOperation`, etc.) in the controller files at `apps/api/v2/src/modules/*/controllers/*.controller.ts`.

### Workflows — removed in this fork

Upstream Cal.com has a Workflows feature (SMS/email reminders and follow-ups) under
`packages/features/ee/workflows/`. **This fork has no `packages/features/ee/` directory at all** —
it was fully removed via `packages/prisma/migrations/20260319000000_drop_workflow_tables/migration.sql`,
which drops `Workflow`, `WorkflowStep`, `WorkflowReminder`, `WorkflowsOnEventTypes`,
`WorkflowsOnTeams`, `WorkflowOptOutContact`, `AIPhoneCallConfiguration`, and related enums. There is
no `Workflow` table in the live schema. Do not reference upstream workflow docs/PRs as if the feature
exists here — reminder/follow-up automation is a genuine product gap, not a config toggle to flip on.

Webhooks (`packages/features/webhooks/`) are unaffected and fully functional — a separate system.

### White-labeling — how it actually works

All white-label config is env-var driven in `packages/lib/constants.ts` — no per-tenant runtime
toggle. Key constants: `APP_NAME`, `COMPANY_NAME`, `EMAIL_FROM_NAME` (defaults to `APP_NAME`),
`LOGO`/`LOGO_DARK`/`LOGO_ICON`, `IS_CALCOM` (hostname-based, false for our domains), `WEBAPP_URL`,
`CAL_URL` (derived from `WEBAPP_URL`). Favicons/PWA icons route through `apps/web/app/api/logo/route.ts`,
which falls back to the `LOGO`/`LOGO_ICON` constants — fixing those constants covers every icon surface.
Brand hierarchy: "MeetSynq" alone in prominent UI (app name, email From-name); "Cuanto Labs" only in
small footer/legal text, never large.

Per-workspace branding removal (a real, separate feature from the above) is the `Team.hideBranding`
column, resolved in `packages/features/profile/lib/hideBranding.ts` — an org's `hideBranding` forces
it for all child teams/users regardless of their own setting. There is **no per-tenant custom-domain
or self-serve multi-tenant white-label feature** — "reselling MeetSynq under your own brand" today
means Cuanto Labs deploying and branding a dedicated instance for that customer, not a toggle inside
a single running app. Reflect this honestly in any marketing copy (see `apps/web/app/white-label/page.tsx`).

### Billing status (as of 2026-09-01)

No subscription/plan billing exists in this codebase — the EE billing layer was stripped along with
Workflows (no billing service directory, no `stripe.subscriptions.create`/`stripe.checkout.sessions.create`
call anywhere in the repo). What's live: Stripe in **live mode**, collecting one-off payments on
individual paid event-type bookings only. `Team`/`OrganizationOnboarding` still carry vestigial
`stripeCustomerId`/`stripeSubscriptionId` columns from the original (unported) org self-serve billing
flow — don't assume they're wired to anything.

Pricing intent (not yet implemented — `apps/web/app/pricing/page.tsx` is marketing copy only, no
checkout): Starter $29/user/mo, Team $79/user/mo, Agency $299/mo flat for 5 users then +$99 per
additional block of 5. Full white-label branding removal is deliberately **excluded** from these 3
self-serve tiers — it's a separate Enterprise/contact-sales plan (matches the white-label page's
"Cuanto Labs deploys a dedicated instance" model). Building real checkout needs: Stripe
Products/Prices (Starter/Team as per-seat prices, Agency as a base item + a `transform_quantity`
package-priced overage item), `Team` schema fields for plan/seat tracking, a Checkout Session
endpoint, a subscription webhook handler, and seat-limit enforcement on invite.
